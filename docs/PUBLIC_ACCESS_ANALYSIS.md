## Мета і контекст

Наразі майже весь сайт закритий для незалогінених користувачів. Мета — відкрити для
всього світу сторінки, які **не потребують користувача** (перегляд турнірів, команд,
гравців, майданчиків, рейтингів), з **урізаним функціоналом**: анонім не бачить дій, що
вимагають гравця (реєстрація майданчика, подання заявки/апеляції, персональні кнопки).

Розділи «Моє» (`/my/*`) та «Модерація» (`/moderator/*`) **не відкриваємо** за жодних умов.

> Цей документ описує плюси та мінуси, ризики й відкриті питання. **Технічні зміни ще не
> внесені.** Реалізація починається лише після прийняття рішень із розділу
> «Відкриті питання».

## Поточний стан: сайт у розробці

**Наразі сайт у розробці, справжніх даних гравців у ньому немає.** Це суттєво змінює
пріоритети ризиків:

- **PII-ризики (витік персональних даних, GDPR-підстава, права суб'єктів) зараз не
  матеріалізовані** — публікувати нема чого. Це вікно, коли механіку відкриття можна
  спроєктувати, впровадити й відпрацювати технічно **без ризику витоку реальних даних**.
- **GDPR і комунікація зі спільнотою стають актуальними до моменту завантаження реальних
  даних / публічного запуску**, а не до внесення коду. Тобто правові рішення (підстава,
  privacy policy, opt-out, noindex) можна ухвалювати паралельно з розробкою, але вони
  **мусять бути готові до появи реальних даних**.
- **Технічні ризики актуальні вже зараз** незалежно від наявності даних: падіння на
  `getUser() === null` (DoS), порядок правил `access_control`, роздільність кешу,
  редірект-петлі, навігація для аноніма. Їх треба закрити в коді відразу.

Практичний висновок: розділити роботу на **технічне відкриття** (можна робити зараз, поки
даних немає) і **чек-лист перед реальними даними** (правові та комунікаційні заходи, які
мають бути виконані до завантаження PII). Див. розділ «Фазування впровадження».

## Поточна модель доступу

- Автентифікація — виключно через Google OAuth (`GoogleAuthenticator`). Локального входу
  за паролем немає.
- Ієрархія ролей: `ROLE_ADMIN` → `ROLE_MODERATOR` → `ROLE_PLAYER` → `ROLE_USER`.
- `ROLE_PLAYER` **не зберігається в БД** — її динамічно надає `PlayerVoter`, якщо в
  `User` є прив'язаний `Player`.
- Контроль доступу — через `access_control` у `config/packages/security.yaml`, за
  URL-префіксами. Правила обробляються зверху вниз, перемагає **перше** співпадіння.
- Наразі публічні (без автентифікації) лише 5 патернів: `/`, `/license`, `/privacy`,
  `/connect/google*`, `/logout`. Усе інше через catch-all `^/` вимагає `ROLE_PLAYER`.
- Атрибут `#[IsGranted]` не використовується ніде; тонший контроль (володіння ресурсом) —
  через Voter'и та inline-перевірки.

## Перелік сторінок

### Відкриваємо (перегляд, без користувача)

| Розділ | URL | Примітка |
|---|---|---|
| Турніри | `/tournaments`, `/tournaments/list` | список з пагінацією/фільтром |
| Турніри | `/tournament/{id}` | картка (лише опубліковані) |
| Турніри | `/tournament/{id}/results`, `/detailed` | результати |
| Турніри | `/tournament/{id}/sessions`, `/sessions/list`, `/sessions/{id}` | сесії |
| Турніри | `/tournament/{id}/disputes`, `/appeals` | лише якщо деталі не приховані (див. нижче) |
| Команди | `/teams`, `/teams/list`, `/team/{id}/tournaments` | |
| Гравці | `/players`, `/players/list`, `/player/{id}`, `/player/{id}/tournaments` | **містить PII** |
| Майданчики | `/venues`, `/venues/list`, `/venue/{id}`, `/venue/{id}/tournaments` | |
| API | `/api/towns/suggest`, `/api/countries/suggest` | для фільтрів «місто»/«країна» на публічних списках |

**Спірки та апеляції.** Логіка `TournamentDisputeAccessService::canView()` вже реалізує
потрібну поведінку: якщо деталі турніру **не приховані** — бачать усі (тепер і аноніми);
якщо приховані — лише офіційні особи, представники та учасники. Для аноніма без гравця в
прихованому турнірі перевірка поверне «немає доступу». Спеціально відкривати чи закривати
нічого не треба — достатньо прибрати падіння на `$user->getPlayer()`.

### Лишаємо закритими

| Розділ | URL | Роль |
|---|---|---|
| Особистий кабінет «Моє» | `/my/*` | `ROLE_PLAYER` + Voter'и |
| Модерація | `/moderator/*` | `ROLE_MODERATOR` |
| Онбординг | `/player-claim*` | `ROLE_USER` |
| Автокомплект гравців | `/api/players/suggest` | `ROLE_USER` |
| Автокомплект команд | `/api/teams/suggest` | `ROLE_PLAYER` |

`/api/players/suggest` і `/api/teams/suggest` використовуються лише у формах створення/
редагування в `/my/*` та модерації — публічним спискам вони не потрібні.

## Ризики безпеки

### 1. Витік персональних даних (найвищий пріоритет)

Профіль `/player/{id}` показує ПІБ і місто, а для декого — контакти (Telegram, Facebook,
телефон). Після відкриття це видно всьому інтернету та пошуковим ботам, а не «залогіненим
учасникам спільноти».

- Контакти зараз віддаються лише модераторам і власнику профілю. Для аноніма
  `isGranted('ROLE_MODERATOR')` дає `false`, тож логіка приховування працює — за умови, що
  контролер не впаде раніше (див. ризик 6).
- ПІБ + місто у відкритому доступі — це персональні дані (детальніше в GDPR-розділі).

### 2. Enumeration через послідовні id

Маршрути `/player/{id}`, `/tournament/{id}` тощо використовують послідовні цілочисельні id.
Відкритий доступ дозволяє будь-кому «прогуляти» весь реєстр простим інкрементом id й
масово зібрати базу ПІБ+місто (scraping) та оцінити її розмір. Раніше для цього треба було
залогінитись і пройти модерацію (мати гравця) — тепер цей бар'єр зникає.

### 3. Rate limiting та ефект NAT

Фактичні ліміти (`config/packages/rate_limiter.yaml`, sliding window):

| Лімітер | Ліміт | Інтервал | Застосування |
|---|---|---|---|
| `read` | 120 | 1 хв | GET-запити без явного `#[RateLimited]` (fallback) |
| `api_suggest` | 60 | 1 хв | suggest-ендпоінти |

Для аноніма ідентичність визначається за IP (userIdentifier відсутній). Наслідки:

- **NAT / спільний IP** (мобільні оператори, корпоративні мережі, Tor-exit): усі анонімні
  відвідувачі з одного IP ділять квоту → легітимні користувачі можуть впертися в 429.
- **Обхід ротацією IP**: скрапер із пулом проксі обходить IP-ліміт. Тобто rate-limit
  відсікає ледачих, але слабкий проти цілеспрямованого зловмисника.

Компроміс: ліміт має бути достатньо низьким проти масового скрапінгу, але достатньо
високим, щоб не бити по живих людях за NAT. Виставити свідомо.

### 4. Публічні suggest-ендпоінти

Відкриваємо `/api/towns/suggest` і `/api/countries/suggest`. Дані малочутливі (довідники
міст/країн). Головний ризик — **помилково** відкрити `/api/players/suggest` (автокомплект
гравців → знову масовий збір ПІБ). Порядок правил у `access_control` критичний: конкретні
`players`/`teams` мають стояти **вище** за будь-яке ширше правило `^/api`.

### 5. CSRF і мутації

Усі мутації (`/my/*`, `/moderator/*`, logout) лишаються за ролями. Правило: **PUBLIC_ACCESS
тільки на GET-перегляд, жоден POST не відкриваємо.** У відкриваних шаблонах кнопки/форми, що
постять у захищені ендпоінти, аноніму не показуємо (інакше поганий UX: клік → редірект на
OAuth). Справжня діра була б лише за випадкового відкриття мутуючого ендпоінта.

### 6. Падіння на `getUser() === null` (потенційний DoS)

Кілька контролерів безумовно роблять `$user = $this->getUser()` і далі
`$user->getPlayer()`. Для аноніма `getUser()` повертає `null` → fatal error → 500.
Підтверджені приклади:

- `Common/Controller/Player/ShowController` — `$currentUser->getPlayer()?->getId()` на
  безумовно приведеному `/** @var User */ $currentUser = $this->getUser()`.
- `Classic/Controller/Tournament/DisputesController`, `Tournament/Appeal/ListController` —
  `$user = $this->getUser(); $player = $user->getPlayer();`.

Це working DoS-вектор: анонім ходить по відкритій сторінці й гарантовано валить 500. Перед
відкриттям треба вичистити **всі** такі місця (grep по `getUser()` у відкриваних
контролерах та в сервісах/маперах, які вони смикають).

### 7. Кеш і роздільність контенту анонім/модератор

Проєкт кешує DTO. Якщо вміст сторінки залежить від ролі (наприклад, контакти в профілі
гравця), а ключ кешу цього не враховує, версія з контактами (для модератора) може
потрапити аноніму або навпаки. Найбезпечніше: контакти не класти в кешований DTO взагалі, а
додавати поверх через `$context` (це збігається з архітектурною рекомендацією). Наразі
`Player/ShowController` формує контакти окремо від кешованого профілю — це треба зберегти.

### 8. Індексація та заголовки безпеки

Відкриті сторінки з PII почнуть індексуватися пошуковиками. Якщо це небажано для профілів —
потрібен `noindex` на `/player/{id}` або відповідні правила robots. CSP та security headers
уже є (`SecurityHeadersSubscriber`); тут змін не треба, головне — не послабити.

## GDPR-аналіз

> **Застереження:** це інженерний розбір, не юридична консультація. Для фінального рішення
> потрібен фахівець із права.

### Що підпадає під регулювання

ПІБ, місто, турнірна історія та контакти — персональні дані. GDPR застосовується незалежно
від того, чи дані вже «десь публічні». Перехід від «видно залогіненим учасникам» до «видно
всьому інтернету + пошуковикам» — це **зміна обробки** (розширення кола отримувачів і мети),
і саме вона потребує обґрунтування.

### 1. Правова підстава (Art. 6)

- **Згода (Art. 6(1)(a)):** якщо гравці погоджувалися в контексті «закритої спільноти зі
  входом через Google», ця згода **не покриває** публікацію у відкритий інтернет — інша
  мета, потрібна нова згода або інша підстава.
- **Легітимний інтерес (Art. 6(1)(f)):** «ведення відкритого спортивного рейтингу» може
  бути легітимним інтересом, але вимагає **balancing test**. Гравець, що реєструвався в
  закритій системі, розумно не очікував публікації ПІБ+міста+телефону в Google — це зважує
  тест не на нашу користь, особливо щодо контактів.

Висновок: публікація **контактів** анонімам найризикованіша. ПІБ+місто в спортивному
рейтингу — сіра зона, залежить від початкової комунікації з гравцями.

### 2. Прозорість (Art. 13–14)

Сторінка `/privacy` вже є. При зміні кола отримувачів даних політику треба **оновити**: хто
тепер бачить дані (весь світ), з якою метою, на якій підставі, як довго. Без цього —
порушення обов'язку прозорості, окремо від питання підстави.

### 3. Право на заперечення та видалення (Art. 17, 21)

За підстави «легітимний інтерес» суб'єкт має право **заперечити проти обробки**. Практично
це означає механізм **opt-out**: прапорець видимості на рівні гравця/користувача, який
ховає профіль від анонімів. Це і найчистіше інженерне рішення, і аргумент на користь
balancing test. Право на видалення загострюється, коли дані публічні та індексовані (кеші
пошуковиків).

### 4. Індексація = підсилення ризику

Після індексації дані легко знаходяться за іменем — саме те, від чого захищає «право бути
забутим», і фактично залучаються треті сторони (пошуковики). Мітигація дизайном: `noindex`
на профілях гравців — дані доступні за прямим посиланням у спільноті, але не спливають у
пошуку за ПІБ.

### 5. Мінімізація даних (Art. 5(1)(c))

Відкривати анонімам **мінімум**: контакти не показувати (лишити модераторам/власнику),
турнірну історію — можна (це суть рейтингу). «Урізаний функціонал для анонімів» — це не лише
UX, а й прямий інструмент мінімізації.

### 6. Діти

Серед гравців «Що? Де? Коли?» реально є неповнолітні (шкільні ліги), а GDPR дає дітям
посилений захист. Ключова проблема: **система наразі ніяк не розділяє повнолітніх і
неповнолітніх гравців** — цих даних просто немає. Тобто технічно відфільтрувати чи окремо
обробити профілі дітей зараз **неможливо**.

Планована позначка «шкільна командо-сесія» (для окремого заліку; ще не реалізована) — це
властивість командо-сесії в контексті заліку, **а не ознака віку конкретного гравця**, і
слабкий проксі: той самий гравець може грати і в шкільній, і в дорослій команді; шкільна
команда не означає, що всі її гравці неповнолітні (і навпаки). Покладатися на неї для
приховування PII дітей не можна.

Наслідок для рішення: оскільки відрізнити дитину від дорослого неможливо, найбезпечніша
позиція — ставитися до відкриття всіх профілів так, ніби серед них є неповнолітні. Це
**посилює** доцільність загальних заходів (`noindex`, opt-out) замість точкових для дітей.
Якщо в майбутньому з'явиться надійна вікова ознака на рівні гравця — можна буде застосувати
суворіший режим саме до неповнолітніх.

## Операційні та продуктові міркування

### Навігація та layout для аноніма

Хедер, меню й футер зараз малюються для залогіненого користувача. Для аноніма треба
продумати: які пункти меню видно, де кнопка «Увійти через Google», що замість блоку
користувача. Якщо в меню лишити посилання на `/my/*`, анонім клікне й отримає редірект на
OAuth — поламаний UX. Порожня чи «поламана» навігація помітна одразу.

### Приховані дії у відкритих шаблонах (інвентаризація)

«Урізаний функціонал» треба інвентаризувати **поіменно**: пройтися по кожному відкриваному
шаблону й скласти список дій, які ховаємо для аноніма (реєстрація майданчика, подання
заявки/апеляції, персональні кнопки на картках турніру/гравця/команди). Інакше — сюрпризи в
навігації та на картках.

### Порожні стани та заклик до дії

Коли анонім бачить сторінку без персональних дій, єдиний доречний CTA — «Увійти через
Google, щоб заявити гравця / створити майданчик / подати результати». Наскільки агресивно
підштовхувати до реєстрації — продуктове рішення.

### Редіректи та петлі

`AccessDeniedHandler` редіректить залогіненого без гравця на `player_claim_index`. Для
аноніма на закритій сторінці Symfony кине на entry point (OAuth). Треба перевірити
відсутність редірект-петель і що після входу користувач повертається туди, куди йшов
(target path).

### HTTP-кеш і проксі

Проєкт за Caddy. HTTP-кешування публічних сторінок спокусливе (анонімний трафік
однорідний), але це класичне джерело витоку «побачив чужі дані», якщо персоналізована
версія залогіненого потрапить у спільний кеш. **Рекомендація: поки що не вводити HTTP-кеш**,
лишити тільки наявний DTO-кеш; зафіксувати як свідоме рішення. Якщо вводити пізніше —
ретельно налаштувати `Vary` та розділення анонім/користувач.

### Логи, аналітика, моніторинг

Анонімний трафік змішається з користувацьким: метрики унікальних відвідувачів і переглядів
стрибнуть — це очікувано. Sentry почне отримувати нові типи помилок від анонімів (зокрема
падіння на `getUser()`, якщо десь пропустимо) — корисно як сигнал під час викатки.

### robots.txt та sitemap

Керувати індексацією можна гранульовано: sitemap для публічних списків
(турніри/команди/майданчики — SEO-плюс для впізнаваності проєкту) та `noindex` на профілях
гравців. Рішення про профілі узгоджується з GDPR-розділом.

### Комунікація зі спільнотою

Гравці реєструвалися в закритій системі. Поява їхніх імен у відкритому доступі без
попередження — GDPR-ризик (розумні очікування) і репутаційний. Потрібен анонс/попередження
**до завантаження реальних даних / публічного запуску**, особливо якщо не робимо opt-out.
Наразі неактуально (даних немає), але має бути в чек-листі перед реальними даними.

## Фазування впровадження

Оскільки публікація PII умовно незворотна (проіндексовані та зіскрапані дані «назад» не
повернути), а зараз реальних даних немає, найрозумніше — розділити роботу в часі.

### Фаза 0 — технічне відкриття (можна робити зараз)

Даних немає, тож PII-ризик не матеріалізований. Реалізуємо механіку та закриваємо технічні
ризики:

- правила `access_control` (тільки GET-перегляд, коректний порядок для `^/api/*`);
- вичищення падінь на `getUser() === null` у всіх відкриваних контролерах;
- навігація та приховані дії для аноніма в шаблонах;
- роздільність кешу анонім/модератор;
- 404 (не 403) для неопублікованого/прихованого;
- e2e-тести на анонімний шлях.

### Фаза 1 — відкриття «неособистого» перегляду

Списки й картки **турнірів, команд, майданчиків** — тут прямих PII мало. Можна відкривати
першими й спостерігати за поведінкою (логи, помилки, навантаження).

### Фаза 2 — профілі гравців (рішення відкладене)

Профілі `/player/{id}` містять ПІБ+місто (PII) і потенційно стосуються неповнолітніх, яких
система не розрізняє. Відкривати — лише після рішення щодо `noindex`, opt-out і мінімізації
(без контактів). Розумно винести в окрему фазу після спостереження за Фазою 1.

### Чек-лист перед завантаженням реальних даних / публічним запуском

Незалежно від коду, до появи PII мають бути виконані:

- [ ] визначена правова підстава (Art. 6) для публічної обробки;
- [ ] оновлена privacy policy (`/privacy`) під нове коло отримувачів;
- [ ] прийняте рішення щодо `noindex` на профілях;
- [ ] прийняте рішення щодо opt-out видимості профілю;
- [ ] прийняте рішення щодо неповнолітніх (за відсутності вікової ознаки);
- [ ] за потреби — анонс/попередження спільноті.

## Рекомендовані рішення й компроміси

| GDPR / ризик | Рекомендоване інженерне рішення |
|---|---|
| Legitimate interest / balancing | Не відкривати контакти анонімам |
| Право на заперечення (Art. 21) | Прапорець видимості профілю (opt-out) |
| Право бути забутим + індексація | `noindex` на профілях гравців |
| Мінімізація даних | Урізаний DTO для анонімів (без контактів) |
| Захист дітей (вік не відстежується) | Загальні `noindex` + opt-out для всіх; суворіший режим — лише коли з'явиться вікова ознака |
| Прозорість (Art. 13) | Оновити `/privacy` |
| DoS на `getUser()` | Вичистити всі безумовні `getUser()->...` у відкриваних контролерах |
| Enumeration / scraping | Свідомо виставити ліміт `read`; за потреби — окремий, суворіший |
| Порядок правил | Тільки GET; `players`/`teams` suggest — вище за PUBLIC-правила `^/api` |
| Навігація для аноніма | Приховати `/my/*`-пункти, додати «Увійти через Google» |
| Витік через спільний кеш | Поки не вводити HTTP-кеш; лишити тільки DTO-кеш |
| Редірект-петлі | Перевірити поведінку `AccessDeniedHandler` + повернення на target path |
| Незворотність публікації PII | Фазування; профілі гравців — окремою фазою після спостереження |

**Рекомендований шлях (мінімум ризику за максимум цінності):** відкрити списки й картки
турнірів/команд/майданчиків (мало прямих PII); профілі гравців відкрити **без контактів +
`noindex`**; закласти **opt-out** прапорець. Це дає публічний рейтинг при контрольованому
GDPR-ризику.

## Відкриті питання для власника та юриста

1. Чи прийнятно, що ПІБ + місто гравців стають публічними та індексованими? (PII/GDPR)
2. Чи додаємо `noindex` на профілі гравців?
3. Чи впроваджуємо opt-out прапорець видимості профілю? Якщо так — увімкнений чи вимкнений
   за замовчуванням?
4. Серед гравців є неповнолітні, але система їх не розрізняє. Чи приймаємо ризик відкриття
   профілів без вікового розділення (покладаючись на загальні `noindex`/opt-out), чи
   відкладаємо відкриття профілів гравців до появи вікової ознаки?
5. Який рівень rate-limit для анонімного `read` прийнятний (компроміс NAT vs scraping)?
6. Хто і коли оновлює текст `/privacy` під нове коло отримувачів даних?

## Технічні кроки реалізації

> Виконуються **після** прийняття рішень вище.

1. **`config/packages/security.yaml`** — додати `PUBLIC_ACCESS` правила вище catch-all
   `^/`, лише для GET-перегляду. Акуратний порядок для `^/api/*`: спершу
   `players`/`teams` suggest (закриті), потім `towns`/`countries` (публічні).
2. **Контролери** — прибрати безумовні `getUser()->getPlayer()`; коректно обробити
   `getUser() === null` у `Player/ShowController`, `Tournament/ShowController`,
   `SessionShowController`, `DisputesController`, `Appeal/ListController` та всіх інших
   відкриваних. Для неопублікованих/прихованих — гарантовано 404, не 403.
3. **Шаблони** — сховати від анонімів дії, що потребують гравця (реєстрація майданчика,
   подання заявки/апеляції, персональні кнопки); показати заклик «увійти через Google».
4. **Кеш** — переконатися, що кешовані DTO не залежать від ролі; контакти додавати поверх
   через `$context`.
5. **Індексація** — за рішенням додати `noindex` на профілі гравців.
6. **`/privacy`** — оновити текст політики.
7. **Тести** — e2e на анонімний доступ: відкриті сторінки віддають 200 без падінь,
   закриті — редірект/403, контакти не витікають аноніму, неопубліковане — 404.
