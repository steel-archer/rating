# Предметна область: «Що? Де? Коли?» і як вона лягає на код

Документ для людей і агентів, які вперше беруться за проєкт: що означають
ігрові терміни, як вони відображені в сутностях і як виглядає повний цикл
турніру. Технічні деталі — у `.kiro/steering/` (сутності, фічі, архітектура).

## Гра коротко

- **Запитання.** Команда має хвилину на обговорення і здає відповідь на бланку.
  Запитання складається з тексту, відповіді, заліку (альтернативних правильних
  відповідей), коментаря, джерел і автора. Бувають дуплети й бліци — кілька
  підзапитань, що зараховуються лише разом.
- **Тур і пакет.** Пакет запитань ділиться на тури; найчастіше це 3 тури по 12
  запитань (буває до 6 турів і до 15 запитань у турі). Результат команди —
  кількість взятих запитань.
- **Команда.** Грає за одним столом; у системі має **базовий склад** на сезон.
  Гравець, що грає за команду, не будучи в її базовому складі, — **легіонер**.
- **Сезон.** Період, до якого прив'язані базові склади. Між сезонами склади
  переносяться командою `app:season:rollover`.

## Формати турнірів

| Термін | У коді | Суть |
|--------|--------|------|
| Очний турнір | `TournamentFormat::Centralized` | Команди грають очно в одному місці (код не обмежує турнір однією сесією) |
| Синхрон | `TournamentFormat::Distributed` | Багато майданчиків відіграють той самий пакет у визначені дати; результати зводяться в одну таблицю |
| Онлайн / офлайн / змішаний | `TournamentOnlineMode` | Чи можуть відіграші бути онлайн; офлайн-турнір не приймає онлайн-майданчики |

Асинхронів (кожна команда грає сама, у зручний час) у системі немає.

## Ролі

| Роль | Звідки береться | Що робить |
|------|-----------------|-----------|
| Гравець | `User` прив'язаний до `Player` (динамічна роль `ROLE_PLAYER`) | Бачить сайт, керує своїми контактами, подає заявки |
| Капітан | `TeamPlayer.isCaptain` | Керує базовим складом команди |
| Організатор | `TournamentOfficial.role = organizer` | Керує турніром, завантажує пакет, схвалює заявки на відіграші |
| Редактор | `TournamentOfficial.role = editor` | Офіційна особа турніру (автор пакета); роль сама по собі не дає прав організатора |
| Ігрове журі | `TournamentOfficial.role = game_jury` | Розглядає спірні відповіді |
| Апеляційне журі | `TournamentOfficial.role = appeal_jury` | Розглядає апеляції |
| Представник майданчика | `VenueRepresentative` | Подає заявки на відіграш синхрону, вносить склади й результати |
| Ведучий | `TournamentSession.host` | Читає запитання на відіграші, має доступ до пакета |
| Модератор / адмін | `ROLE_MODERATOR` / `ROLE_ADMIN` у `User.roles` | Модерує заявки, турніри, майданчики, блокує користувачів |

Адмін не має автоматичного доступу до дій, що залежать від зв'язків
(організатор, представник, ведучий, журі): ці права перевіряються саме через
зв'язок.

## Відповідність термінів і сутностей

| Термін | Сутність / поле |
|--------|-----------------|
| Турнір | `Tournament` (тури: `toursCount`, `questionsPerTourMap`) |
| Пакет запитань | `TournamentDocument` (файли), завантаження — `TournamentDocumentDownload` |
| Відіграш (сесія) | `TournamentSession` — турнір на конкретному майданчику з ведучим і датою |
| Заявка на відіграш | `SessionClaim` (`pending` → `approved` / `rejected` / `revoked`) |
| Склад команди на відіграші | `TournamentSessionTeam` + `TournamentSessionTeamPlayer` (`isLegionary`, `isCaptain`) |
| Відповідь команди | `TournamentSessionTeamAnswer` (`questionNumber`, `isCorrect`) |
| Спірна відповідь (спірна) | Поля `dispute*` на `TournamentSessionTeamAnswer` (окремої сутності немає) |
| Апеляція | `Appeal` (`accept` — зарахувати відповідь, `remove` — зняти запитання) |
| Базовий склад | `TeamPlayer` на сезон; переходи — `TeamPlayerTransfer` |
| Майданчик | `Venue` (+ `VenueRepresentative`) |

## Повний цикл синхрону

1. **Створення.** Гравець створює турнір (чернетка), стає його організатором,
   призначає офіційних осіб і задає дати: реєстрації, проведення, подання
   результатів, апеляцій, приховування результатів і деталей.
2. **Модерація і публікація.** Організатор подає турнір на модерацію →
   модератор схвалює або відхиляє з коментарем → після схвалення організатор
   окремо публікує турнір.
3. **Пакет.** Організатор завантажує файли пакета.
4. **Заявки на відіграш.** До дедлайну реєстрації представник майданчика подає
   заявку (одразу створюються сесія і заявка зі статусом `pending`) і
   призначає ведучого. Організатор схвалює, відхиляє або відкликає заявку;
   відхилену можна схвалити пізніше.
5. **Підготовка ведучого.** Ведучий схваленого відіграшу завантажує пакет.
   Кожне завантаження фіксується; історія ведучих зберігається.
6. **Гра і результати.** Після гри представник вносить склади (з новими
   командами/гравцями, разовими назвами, капітаном; легіонери визначаються
   автоматично), відповіді (XLSX-шаблон) і спірні, а потім подає результати до
   дедлайну. Актуальний чи колишній ведучий, який завантажував пакет, не може грати в цьому
   турнірі.
7. **Спірні.** Ігрове журі приймає (відповідь стає правильною) або відхиляє
   спірні; бали перераховуються.
8. **Апеляції.** Учасники до дедлайну апеляцій подають апеляції; апеляційне
   журі зараховує відповідь або знімає запитання для всього турніру; бали
   перераховуються.
9. **Підсумок.** Результати й деталі по запитаннях приховані від
   неофіційних осіб до заданих дат (захист від спойлерів синхрону). Підсумкова
   таблиця використовує дробові місця для однакових результатів.

Очний турнір проходить той самий шлях з такими відмінностями: заявки й подання
результатів відкриті, поки турнір опублікований (без дедлайнів), спірних і
апеляцій через систему немає, а режим `mixed` для нього заборонений.

## Порівняння з rating.chgk.info

Проєкт — український аналог рейтингового сайту МАІІ. Стан на 2026-10-02:

| Можливість | rating.chgk.info | Тут |
|------------|------------------|-----|
| Турніри, очні й синхронні | є | є |
| Асинхрони | є | немає |
| Заявки представників на синхрони, ведучі | є | є |
| Спірні й апеляції | є | є |
| Базові склади, легіонери, переходи | є | є (переходи зберігаються, окремої сторінки історії немає) |
| Майданчики | є | є (з модерацією) |
| Рейтинг команд і гравців, релізи рейтингу | є | **немає** — поля `difficulty` / `trueDl` є, розрахунку немає |
| Публічний перегляд без входу | є | немає — публічні лише головна, ліцензія й політика конфіденційності; після Google-входу без прив'язаного гравця доступна тільки заявка на прив'язку, решта вимагає гравця (план — `docs/PUBLIC_ACCESS_ANALYSIS.md`) |
| Публічне API | є | немає (лише внутрішні AJAX-ендпоінти) |
| Вхід | логін/пароль | лише Google OAuth |
